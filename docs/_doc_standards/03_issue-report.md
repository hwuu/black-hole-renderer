# 专项标准：问题报告（issue 文档）（03）

## 文件说明

本文件约束 `docs/issues/`（及同类路径）下的**问题记录**文档：聚焦现象、影响与已知事实，与正式设计文档的边界划分清楚。须与 [`00_overall.md`](00_overall.md) **一致**。

---

## 1. 文档定位

问题报告用于：

- 固化**现象、影响、范围、已知事实**与**待澄清问题**；  
- 为后续设计文档或变更提供输入，**不必**在同一篇内完成最终方案（若写草案须明确标注）。  

若某主题已形成冻结设计，问题文中应**链接**到设计真源，避免双份矛盾叙述。

---

## 2. 推荐结构

可按需裁剪，建议包含：

1. **定位**：本文记录什么问题；**不**承载哪些内容（如「不含冻结方案」）。  
2. **现象 / 复现**：用户或系统可见行为；若无法稳定复现，写明条件与频率。  
3. **影响**：对功能、安全、运维、数据一致性等的影响（可用表格按维度列出）。  
4. **范围**：影响的组件、路径、版本或环境。  
5. **已知事实**：代码路径、配置、日志行为等可核对事实；区分事实与推断（见 `00_overall` 2.2）。  
6. **待回答的问题**：开放问题列表，供评审或设计跟进。  
7. **关联**：相关 PR、内部工单、设计文档链接（真实存在者，勿编造单号）。  

若正文包含**方案草案**，须标明「草案 / 未评审」，并优先在冻结后迁入设计文档、本文仅保留链接与结论摘要。

---

## 3. `resolved/` 下已闭环文档

建议补充（可与上文合并为「闭环」一节）：

- **解决方式**：改了什么（行为或配置层面一句话 + 可选链接）。  
- **版本或时间范围**：从何时起可按本文描述视为已处理（若适用）。  
- **残留风险或监控**：若仍有限制或需观察项，明确写出。  

---

## 4. 与全局标准的关系

诚信、引用、术语与文风要求见 [`00_overall.md`](00_overall.md)。问题报告尤其避免把推断写成已验证事实。

---

## 5. 专项检查清单

- 是否写清「本文含 / 不含」方案与真源链接。  
- 事实与推断是否分开；待决问题是否列出。  
- 已闭环文档是否包含解决方式与残留风险（若有）。
