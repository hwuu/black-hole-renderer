# 专项标准：笔记、提议与其他短文（04）

## 文件说明

本文件约束未单独设专项模板的短文，常见于 `docs/notes/`、文件名含 `proposal`、`scratch`、`*_draft*` 等。须与 [`00_overall.md`](00_overall.md) **一致**。

---

## 1. 文档类型区分

| 类型 | 用途 | 典型状态 |
|------|------|----------|
| **笔记** | 调研摘录、调试记录、草稿思路、会议备忘 | 草稿、个人或小组可读，**不**冒充冻结设计 |
| **提议** | 待评审的改法或决策包：动机、选项、推荐、影响 | 待评审 / 已采纳 / 已废弃 / 已合并至他文 |
| **其他短文** | ADR 片段、临时 runbook、一次性说明 | 在文首标明时效与替代链接（若有） |

### 1.1 何时停留在 04，何时升级

- **继续留在 04**：仍是预研、草稿、方案摸底、个人或小组讨论材料，尚未作为共同评审依据或实施依据。  
- **升级到 `01_technical_design.md`**：文档已开始承担正式设计职责，例如定义目标方案、关键边界、跨组件约定，并将作为后续评审或实现的共同依据。  
- **升级到 `02_implementation-tracking.md`**：文档重点已转为里程碑范围、验收、执行计划或实施跟踪。  

---

## 2. 文首建议字段

至少用数行说清：

- **状态**：草稿 / 提议待评审 / 已实施 / 已过期 等。  
- **日期或版本**：最近一次有意义更新日期（可选：实施或验证日期）。  
- **若与正式设计相关**：链向设计真源；若已被设计吸收，写明「内容已合并至某某，本文仅作历史」。  

---

## 3. 提议类最低内容

提议（proposal）建议包含：

1. **背景与问题**：要解决什么。  
2. **可选方案**：至少两个或有意识的「维持现状」对照；每选项含主要利弊。  
3. **推荐与理由**：工程判断须标明（见 `00_overall` 2.2）。  
4. **影响面**：代码路径、运维、迁移、兼容性。  
5. **实施概要**：步骤或阶段（不必等于最终任务分解）。  
6. **状态与后续**：评审结论写回文首或本节，避免正文与状态长期不一致。  

---

## 4. 笔记类底线

- 允许不完整，但须避免**与冻结设计矛盾**而不加说明；若发现冲突，应标注「与某某文档不一致，待确认」。  
- 摘录外部资料时，尽量给出来源或链接，便于复核（见 `00_overall` 第 3 节）。  

---

## 5. 与全局标准的关系

禁止编造数据、套话与过深无意义标题等，一律遵循 [`00_overall.md`](00_overall.md)。

---

## 6. 专项检查清单

- 文首状态与日期是否清楚。  
- 提议是否具备选项对比与推荐理由。  
- 是否误将草稿当作已冻结设计（缺少链接与状态说明）。  
- 是否已经跨过「探索性材料」边界，实际应升级到 `01` 或 `02`。
