# 专项标准：技术设计文档（01）

## 文件说明

本文件约束**技术设计、架构与方案类**文档（例如 `docs/design/` 下的设计稿）。全文须与全局底线 [`00_overall.md`](00_overall.md) **一致**；若某业务域另有补充标准，还应同时满足其中与术语、组件命名及场景化相关的约定。

---

## 1. 适用与目标读者

适用于需要说明「问题—分析—方案—落地/演进」的设计文档。目标是让读者能评审架构取舍、边界与风险，并能对照实现。

---

## 2. 与全局标准的关系

- 信息分类、证据与引用、诚信、文风负面约束、标题层级建议等，一律遵循 [`00_overall.md`](00_overall.md)。  
- 本文件只补充：**推荐章节骨架**、**长文档拆分**、**目录与编号习惯**，以及常见信息架构反模式。

### 2.1 何时用 01，而不是 02 或 04

- **核心问题是“系统怎么设计、为什么这样设计、边界怎么划”**：用本文件。  
- **核心问题是“本轮做什么算完成、执行顺序怎么排、进度到哪”**：改用 [`02_implementation-tracking.md`](02_implementation-tracking.md)，即使文件放在 `design/` 路径下。  
- **仍是探索性 proposal / 草稿 / 预研笔记，尚未成为共同评审依据或实施依据**：先用 [`04_misc.md`](04_misc.md)。  
- **若 proposal 已进入正式评审，并将作为后续实现、联调或跨组件约定的共同依据**：应升级为技术设计文档，并按本文件组织。  

---

## 3. 推荐章节骨架（可裁剪）

下列骨架适用于「问题分析 + 方案设计」类长文；主题单一时可合并章节，但须保留「问题 → 分析 → 方案/结论」的逻辑链。

### 3.1 问题陈述

建议包含：背景、现状分析、风险评估。多根因时在背景中列出 `P1/P2/...`（见 `00_overall` 2.4）。

### 3.2 分析与调研

回答「为何选后续方案」：设计目标、机制对比、业界或替代方案对比、选型结论。  
**注意**：认证方式、产品能力边界、官方行为等放在本章，避免塞进「方案设计」导致主线混杂。

### 3.3 方案设计

回答「目标架构或目标行为是什么」：原则、总览、关键模型、接口或数据边界、技术选型等。

### 3.4 过渡方案（若存在）

回答「当前阶段如何落地」：须明确标注为过渡；写清哪些可复用、哪些将被替换（见 `00_overall` 2.5）。

### 3.5 实施计划（若需要）

阶段划分、依赖、验证方式、回滚或降级思路；每阶段尽量包含目标、任务、依赖、如何验收。

### 3.6 附录

仅放支撑材料：命令清单、长配置、协议细节、背景知识。**禁止**把选型结论、关键根因、理解主方案必需的内容塞进附录当「收纳筐」。

### 3.7 参考资料

关键外部论断集中列出，格式见 `00_overall` 第 3 节。

---

## 4. 长文档的信息架构

单文件过长时，建议拆分而非堆叠目录：

- **主文档**：单一主线——「目标模型 + 必须共同遵守的约定」。  
- **派生文档**：迁移指南、测试用例清单、分组件落地清单、FAQ 等，从文首链回主文档。  

避免在同一篇内长时间交织「原则陈述、动机论证、分组件要求、迁移步骤」且缺少小标题边界，导致读者无法判断当前段落属于**规范**还是**说明**还是**操作步骤**。

---

## 5. 目录与标题层级

- 遵循 `00_overall`：标题层级**建议不超过三级**；避免 `1.1.1.1` 式仅为排版对称的深层编号。  
- 目录与正文编号保持一致；避免目录出现跳号（如仅有 `5.5` 而无 `5.1`）且与正文不对应。  

---

## 6. 常见信息架构反模式（自查）

撰写或评审时可对照下列现象，考虑拆章、前移「非目标」或移到附录：

- 原则、动机、对各模块要求、迁移建议在同一章内无标记地切换。  
- 同一约束在「引用块 + 列表 + 小结」中重复多遍而无新增信息。  
- 附录承载主线推理或选型结论。  

---

## 7. 专项检查清单（设计类）

除 `00_overall` 第 10 节外，另查：

- 调研与选型是否集中在「分析与调研」，而非散落在「方案设计」段尾。  
- 过渡方案与目标方案是否命名清楚、边界清楚。  
- 架构图是否分目标态/过渡态（若两者并存）。  
- 若该业务域另有补充标准，是否同时满足其中与本文主题相关的条款。
